# Web Stack: React + TanStack Start

Source URL: Internal draft
Collected: 2026-04-15
Published: 2026-04-15
Updated: 2026-05-22
Status: Draft
Scope: React and TanStack Start web applications. This draft covers both fullstack products and frontend-owned products that do not own server-side persistence or authentication. In this document, "frontend-owned" means a TanStack Start app that may still run SSR, prerendered routes, BFF-style integration points, and a Nitro app server, but does not own a product database, auth server, or server-side domain model. It does not mean static-only hosting unless this standard later adds an explicit static export deployment contract. Unless a rule explicitly says "fullstack", "database", "server function", or "production deployment", it applies to both frontend-owned and fullstack apps adopting this stack.

Version verification: API examples that touch TanStack Start server entry, hydration, Router SSR nonce handling, TanStack Form validators, or `nuqs` TanStack Router integration must be re-verified against the exact package versions used by each product before copying into production code. This draft intentionally records the organization standard and known integration shape, not a guarantee that fast-moving upstream APIs are unchanged.

## 1. Runtime & Toolchain

### 1.1 Runtime: Bun

All products adopting this standard run on **Bun** as the JavaScript runtime, package manager, script runner, and baseline test runner. Application builds still use the TanStack Start/Vite/Nitro toolchain generated by the standard scaffold.

- Use `bun` for all script execution, dependency installs, and project builds.
- Do not use Node.js as the application runtime, and do not use npm, yarn, or pnpm as package managers in any project adopting this standard.
- Bun's built-in test runner (`bun test`) is the baseline. Vitest may be layered on top only when richer React/component test utilities are required; the required `test` script must make the chosen test runner explicit.

### 1.2 Container: Docker + Docker Compose

Every product is containerized.

- Each product ships a `Dockerfile` at the repo root.
- A `docker-compose.yml` (or `docker-compose.yaml`) is required for local development, covering the app and any required supporting services such as PostgreSQL, Redis, or queues.
- Do **not** bake secrets or environment values into Docker images. Runtime configuration is injected through environment variables at container startup.
- Base image: `oven/bun` (official Bun image). Pin to a specific version tag, never `latest`.
- Frontend-owned products may omit database, queue, and cache services from Compose when they are not required, but the app container contract still applies.

### 1.3 Outside-facing gateway: Nginx required

TanStack Start must never be exposed directly to outside traffic in staging or production. Every deployed product adopting this stack must include Nginx as the outside-facing gateway in the Docker deployment.

Rules:
- The TanStack Start app container listens only on the internal Docker network.
- The app container uses `expose:`, not host-facing `ports:`.
- The Nginx container is the only service that binds host ports (`80` / `443`).
- All browser traffic flows through Nginx before reaching TanStack Start.
- Nginx owns TLS termination, HTTP/2, Brotli/Gzip compression, baseline security headers, CSP nonce generation/forwarding, static asset caching, rate limiting, and upstream proxy retry behavior.
- Direct external access to the Bun/TanStack Start server is banned because it bypasses the security and delivery controls owned by Nginx.
- Baseline deployment proxies all application and asset requests to the internal app container unless the standard Nginx image contract is extended to copy `.output/public` or an equivalent built asset directory into the Nginx image. Do not invent a per-project asset-copy flow in the application Dockerfile.

### 1.4 Standard Dockerfile contract

Every project adopting this stack must use the same Dockerfile structure. Project-specific behavior belongs in `package.json` scripts and runtime environment variables, not in custom Dockerfile flows.

Required files:

```text
Dockerfile
.dockerignore
docker-compose.yml
public/
nginx/
  Dockerfile
  nginx.conf.template
  entrypoint.sh
```

Rules:
- The app image uses `oven/bun:<pinned-version>`. Never use `latest`.
- The app Dockerfile uses a multi-stage build: `deps`, `build`, and `runtime`.
- The `deps` stage installs full dependencies because build tooling usually lives in `devDependencies`.
- The `runtime` stage installs production dependencies only with `bun install --production --frozen-lockfile`.
- The final runtime image must not include dev dependencies.
- The final runtime image must not include `.env`, secrets, local caches, test reports, or source control metadata.
- Runtime configuration is injected through environment variables at container startup.
- The runtime container runs as a non-root user.
- The app image may declare `EXPOSE 3000`, but Docker Compose must use internal `expose:`, not host-facing `ports:`.
- `public/` is a required project directory. Keep it in the repo even when empty so the standard Dockerfile remains identical across products.

Required `package.json` script contract:

```json
{
  "scripts": {
    "dev": "...",
    "build": "...",
    "start": "...",
    "typecheck": "...",
    "lint": "...",
    "test": "..."
  }
}
```

The Dockerfile must call only the standard scripts:

```dockerfile
RUN bun run build
CMD ["bun", "--bun", "run", ".output/server/index.mjs"]
```

This keeps the Dockerfile identical across projects. Nitro app-server output is the organization-standard TanStack Start deployment target. The standard Dockerfile assumes a running app server backed by Nitro-style output in `.output`; if the organization changes deployment targets or adopts static export, update this stack standard before changing per-project Dockerfiles.

Production containers must run the built Nitro app-server entry directly with `bun --bun run .output/server/index.mjs`. Do not use `bun run start` as the Docker runtime command because script indirection can hide dev-server behavior, source TypeScript transpilation, framework-specific assumptions, or dependencies installed only in `devDependencies`. The `start` script may exist for local/manual production-mode runs, but if present it must match the same built-output command. Project-specific startup flags belong in environment variables, not in custom Dockerfile commands. Static export is not part of this baseline unless this standard is updated with a separate static deployment contract.

Script behavior rules:
- `dev` starts the local development server and may watch files.
- `build`, `typecheck`, `lint`, and `test` must be non-watch commands suitable for CI and Docker usage.
- `test` must run the default automated test suite for the project. If multiple suites exist, add explicit scripts such as `test:unit`, `test:component`, or `test:e2e` and keep `test` as the baseline suite required before merge.

Every product using the running Nitro app-server baseline must expose an unauthenticated internal readiness endpoint at `GET /ready`. It must return `2xx` only when the app process is alive and required local dependencies for serving traffic are available. The response body should be minimal, for example `ok`, and must not include secrets, build metadata, dependency details, stack traces, or environment dumps. Nginx and container health checks may call this endpoint on the internal network; do not present it as an operator diagnostics endpoint. If this standard later adds static export, define a separate health-check contract for that deployment mode.

#### Standard TanStack Start Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

FROM oven/bun:<pinned-version> AS deps
WORKDIR /app

COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

FROM deps AS build
WORKDIR /app

COPY . .
RUN bun run build

FROM oven/bun:<pinned-version> AS runtime
WORKDIR /app

ENV NODE_ENV=production
ENV HOST=0.0.0.0
ENV PORT=3000

COPY package.json bun.lock ./
RUN bun install --production --frozen-lockfile

COPY --from=build --chown=bun:bun /app/.output ./.output
COPY --from=build --chown=bun:bun /app/public ./public

USER bun

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD bun -e "fetch('http://127.0.0.1:3000/ready').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

CMD ["bun", "--bun", "run", ".output/server/index.mjs"]
```

Notes:
- `bun install --production --frozen-lockfile` belongs in the `runtime` stage, not the `deps` stage.
- The `deps` and `build` stages need dev dependencies because build tooling usually lives in `devDependencies`.
- The `.output` path is required because Nitro is the organization-standard deployment target. Preserve the Dockerfile contract by building through the standard `build` script and running the generated `.output/server/index.mjs` entry directly rather than creating project-specific Dockerfile flows. Static export requires a separate deployment contract and is not part of this baseline.
- Before shipping a product image, run the final runtime image and verify that `bun --bun run .output/server/index.mjs` works with production dependencies only. If the generated Nitro output or startup command requires a package currently listed in `devDependencies`, move that package to production dependencies or change the generated runtime path before release.

## 2. Framework & Ecosystem

### 2.1 Framework: TanStack Start

**TanStack Start** is the required React web framework for all products adopting this stack. It is fullstack-capable, but products may use it for frontend-owned apps when server-side persistence, owned authentication, or server functions are not needed.

- File-based routing via **TanStack Router** (built into Start).
- SSR with streaming by default.
- For fullstack apps, server functions replace REST API controllers. Do not build a separate Express/Hono API layer unless there is an explicit integration reason.
- Frontend-owned apps may use TanStack Start for routing, SSR, prerendered routes served by the Start/Nitro app-server deployment, and BFF-style integration points without owning a database or auth server. Static-only export is not included in this baseline.
- TanStack Router handles all client-side navigation. Do not use React Router or Next.js.

**Project initialization is required via the TanStack CLI.** Do not scaffold a project from scratch or copy from an existing project manually.

```bash
bunx --bun @tanstack/cli@latest create my-app \
  --framework react \
  --package-manager bun \
  --toolchain eslint \
  --no-examples \
  -y
```

This Bun-first command is the organization-standard way to invoke the TanStack CLI for new projects. Upstream documentation may show `npx @tanstack/cli create my-app` or `tanstack create my-app`; products adopting this stack use `bunx --bun` and explicit flags so project creation follows the same runtime and package-manager standard as the generated application.

This ensures a unified, up-to-date project structure across all products and makes engineer onboarding consistent. Post-init steps (Shadcn preset, route cleanup) follow the standard project init runbook.

Generation-tool rule: `@latest` is allowed only for one-time project generation commands such as the TanStack CLI and Shadcn CLI. Generated files and lockfile changes must be reviewed before merge. Production dependencies in `package.json` remain pinned by the supply-chain rules.

### 2.1.1 Project folder structure

Every product adopting this stack must use the standard folder structure below unless a product-level ADR documents an exception. TanStack Start requires `src/routes/`, `src/router.tsx`, and generated `src/routeTree.gen.ts`; the remaining structure is the organization standard for keeping route wiring, pages, features, and shared infrastructure separated as products grow.

```text
src/
  routes/
    __root.tsx
    index.tsx
    <segment>/
      route.tsx
      index.tsx
      $param.tsx
    _<group>/
      route.tsx
      index.tsx
    $.tsx
  pages/
    HomePage.tsx
    products/
      ProductsPage.tsx
      ProductDetailPage.tsx
  components/
    ui/
    layout/
    shared/
  features/
    <domain>/
      components/
      hooks/
      queries/
      mutations/
      schema.ts
      types.ts
  lib/
    auth.ts
    auth-client.ts
    csp.ts
    env.ts
    utils.ts
  db/
    index.ts
    schema.ts
    migrations/
  server/
    functions/
    services/
  styles/
    app.css
  router.tsx
  routeTree.gen.ts
public/
nginx/
  Dockerfile
  nginx.conf.template
  entrypoint.sh
```

Rules:
- `src/routes/**` contains route modules only: `createFileRoute`, `createRootRoute`, loaders, `beforeLoad`, `validateSearch`, `head`, route metadata, server route handlers, and route-level wiring.
- Page components live under `src/pages/**`. Route modules must import page components from `src/pages/**`; do not define page components inline in route files.
- Page files must use `getRouteApi('/route/path')` for typed params, search, loader data, and route context. Do not import `Route` from the route module into the page component because that creates circular imports and can hurt code splitting.
- Root and layout shell components may live in `src/components/layout/**` when they are reused or large. Tiny `__root.tsx` document-shell wiring may stay in the root route file because it is application shell, not a page component.
- Reusable Shadcn UI primitives live in `src/components/ui/`.
- App layout components live in `src/components/layout/`.
- Cross-feature shared components live in `src/components/shared/`.
- Domain-specific reusable code lives in `src/features/<domain>/`. Pages compose features; features must not depend on pages.
- Shared framework and app helpers live in `src/lib/`.
- Fullstack database code lives in `src/db/`.
- Server-only functions and services live in `src/server/` unless they are TanStack Start server route handlers owned by `src/routes/**`.
- Global CSS and Tailwind theme entry live in `src/styles/app.css` or the scaffold's equivalent CSS entry.
- `src/routeTree.gen.ts` is generated by TanStack Router and must never be hand-edited.

### 2.1.2 Route file organization

TanStack Router supports both flat dotted route filenames and folder-based route files. Products adopting this standard must use the folder/sub-folder model because it keeps route trees navigable as products grow and keeps route modules grouped by URL/domain.

Rules:
- Use `src/routes/<segment>/<child>.tsx` for nested URL segments.
- Use `src/routes/<segment>/route.tsx` for directory layout routes that wrap child routes.
- Use `$paramName.tsx` for dynamic path params inside the matching folder.
- Do not use flat dotted route files such as `store.$slug.tsx` or `dashboard.orders.$orderId.tsx`.
- The path passed to `createFileRoute()` must match the folder-based route location generated by TanStack Router.
- Keep `__root.tsx` and top-level `index.tsx` at the route root.
- Keep page rendering in `src/pages/**`; route files should wire the page component rather than defining it inline.

Correct:

```text
src/routes/store/$slug.tsx              -> /store/$slug
src/routes/dashboard/orders/index.tsx   -> /dashboard/orders
src/routes/dashboard/orders/$orderId.tsx -> /dashboard/orders/$orderId
src/routes/admin/users/index.tsx        -> /admin/users
```

Banned:

```text
src/routes/store.$slug.tsx
src/routes/dashboard.orders.$orderId.tsx
src/routes/admin.users.index.tsx
```

Example route module:

```typescript
// File: src/routes/store/$slug.tsx
import { createFileRoute } from '@tanstack/react-router'
import { StorePage } from '../../pages/store/StorePage'

export const Route = createFileRoute('/store/$slug')({
  component: StorePage,
})
```

Example page module:

```tsx
// File: src/pages/store/StorePage.tsx
import { getRouteApi } from '@tanstack/react-router'

const routeApi = getRouteApi('/store/$slug')

export function StorePage() {
  const { slug } = routeApi.useParams()
  return <main>{slug}</main>
}
```

### 2.1.3 Deferred hydration

Deferred hydration is required where applicable for TanStack Start pages. Use it for non-critical SSR content and heavy widgets that should be visible, styled, and indexable immediately but do not need immediate interactivity.

Applicability must be explicit in review. A page needs a deferred hydration decision when it includes below-the-fold interactive sections, browser-only widgets, charts, embeds, editors, maps, carousels, or any client component that materially increases startup JavaScript. If no boundary is useful, note why in the PR instead of adding a meaningless boundary.

Use `Hydrate` from `@tanstack/react-start` with strategies from `@tanstack/react-start/hydration` after verifying these imports against the product's pinned TanStack Start version. By default, `Hydrate` also splits the children into a deferred JavaScript chunk, reducing initial startup JavaScript and hydration work.

Good candidates:
- Below-the-fold reviews, comments, FAQs, related products, long marketing sections, and product detail sections.
- Heavy widgets such as charts, carousels, maps, video players, editors, previews, embeds, or analytics panels.
- Intent-gated panels such as filters, preview panes, contextual tools, and command/search helpers.
- Static server-rendered content that should remain visible and indexable but does not need to hydrate on initial document load.

Poor candidates:
- Primary navigation, route chrome, search boxes, account controls, and consent controls.
- Above-the-fold forms, add-to-cart buttons, checkout actions, payment actions, or other money/data-loss controls.
- Interactive LCP or hero content that users may click immediately.
- Accessibility-critical controls that must be keyboard-ready as soon as the page appears.
- Components whose props, context, or shared state must update immediately after startup.

Common patterns:

```tsx
import { Hydrate } from '@tanstack/react-start'
import { idle, interaction, never, visible } from '@tanstack/react-start/hydration'

export function ProductPage() {
  return (
    <>
      <ProductHero />
      <BuyBox />

      <Hydrate when={visible({ rootMargin: '800px' })} prefetch={idle()}>
        <BelowFoldReviews />
      </Hydrate>

      <Hydrate
        when={interaction({ events: ['focusin', 'click'] })}
        prefetch={visible({ rootMargin: '1200px' })}
      >
        <RecommendationCarousel />
      </Hydrate>

      <Hydrate when={never()}>
        <StaticTrustBadges />
      </Hydrate>
    </>
  )
}
```

Rules:
- Import `Hydrate` statically from `@tanstack/react-start`.
- Render the imported `Hydrate` tag directly, or use an import rename. Do not assign it to another component variable if child chunk splitting is expected.
- Keep the component you want to split directly inside `Hydrate`.
- Do not hide split boundaries behind wrapper components if child chunk splitting is required.
- Move hook calls into a named child component inside the boundary; do not call hooks directly in extracted JSX.
- Use `split={false}` only when the child code is small, already in the startup bundle, or cannot be safely extracted.
- Use `prefetch` when a chunk, query, or other async resource should start loading before hydration.
- Measure each boundary. A boundary is only successful if it reduces startup JavaScript or hydration work without delaying expected interactions.
- Every page with heavy, below-the-fold, or intent-gated UI must include a deferred hydration review before merge. Confirm which parts must be interactive immediately, which SSR-rendered parts can wait for `visible()`, `idle()`, `interaction()`, `media()`, `condition()`, or `never()`, and whether the chosen boundary blocks primary user tasks, keyboard access, checkout/payment actions, or auth/account controls.

### 2.1.4 App-level CSP nonce

Every TanStack Start app adopting this stack must include app-level CSP nonce plumbing so it is ready for staging and production nonce-based CSP. In staging and production, infrastructure generates and forwards the nonce; the application is responsible for reading it, passing it through TanStack Start context, and applying it to TanStack Router SSR.

Mandatory files and responsibilities:
- `src/server.ts` reads `x-csp-nonce` from the request header and passes `{ nonce }` into Start context.
- `src/lib/csp.ts` exposes `getCspNonce()` as an isomorphic helper.
- `src/router.tsx` configures TanStack Router with `ssr.nonce: getCspNonce()`.
- The root document emits `<meta property="csp-nonce" content={nonce} />` only when a nonce exists and when the client helper depends on DOM lookup.
- The client-side nonce reader returns `undefined`, not an empty string, when no nonce meta tag exists.

Rules:
- Treat CSP nonce as an app-level SSR requirement, not only an Nginx/security-header setting.
- Do not hardcode or reuse nonce values across requests.
- Do not generate a separate client nonce; SSR and hydration must use the same request nonce.
- Product-specific CSP sources may extend the policy, but must preserve nonce-based `script-src`.

#### Internal reference implementation

This is the organization-owned reference implementation for CSP nonce plumbing in TanStack Start. TanStack Start does not provide an explicit default CSP nonce guide, so this stack owns the convention to keep projects consistent. This pattern is required, but the exact imports and context APIs are version-sensitive. During each stack refresh and before each new product scaffold, verify this section against the current pinned TanStack Start and TanStack Router releases.

`src/server.ts`

```typescript
import handler, { createServerEntry } from '@tanstack/react-start/server-entry'

export default createServerEntry({
  fetch(request) {
    const nonce = request.headers.get('x-csp-nonce') || undefined

    return handler.fetch(request, {
      context: { nonce },
    })
  },
})
```

`src/lib/csp.ts`

```typescript
import {
  createIsomorphicFn,
  getGlobalStartContext,
} from '@tanstack/react-start'

export const getCspNonce = createIsomorphicFn()
  .server(() => {
    const ctx = getGlobalStartContext()
    return (ctx as { nonce?: string } | undefined)?.nonce
  })
  .client(() => {
    const el = document.querySelector<HTMLMetaElement>(
      'meta[property="csp-nonce"]',
    )

    return el?.content || undefined
  })
```

`src/router.tsx`

```typescript
import { createRouter as createTanStackRouter } from '@tanstack/react-router'
import { getCspNonce } from './lib/csp'
import { routeTree } from './routeTree.gen'

export function getRouter() {
  const router = createTanStackRouter({
    ssr: {
      nonce: getCspNonce(),
    },
    routeTree,
    scrollRestoration: true,
    defaultPreload: 'intent',
    defaultPreloadStaleTime: 0,
  })

  return router
}
```

`src/routes/__root.tsx`

```tsx
import {
  HeadContent,
  Outlet,
  Scripts,
  createRootRoute,
} from '@tanstack/react-router'
import type { ReactNode } from 'react'
import { getCspNonce } from '../lib/csp'

export const Route = createRootRoute({
  component: RootComponent,
})

function RootComponent() {
  return (
    <RootDocument>
      <Outlet />
    </RootDocument>
  )
}

function RootDocument({ children }: { children: ReactNode }) {
  const nonce = getCspNonce()

  return (
    <html suppressHydrationWarning>
      <head>
        {nonce ? <meta property="csp-nonce" content={nonce} /> : null}

        <script
          nonce={nonce}
          dangerouslySetInnerHTML={{
            __html: `
              (() => {
                const stored = localStorage.getItem('theme') || 'system';
                const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
                const dark = stored === 'dark' || (stored === 'system' && prefersDark);
                document.documentElement.classList.toggle('dark', dark);
              })();
            `,
          }}
        />

        <HeadContent />
      </head>
      <body>
        {children}
        <Scripts />
      </body>
    </html>
  )
}
```

Optional JSON-LD helper:

```tsx
import { getCspNonce } from './csp'

export type JsonLdValue =
  | string
  | number
  | boolean
  | null
  | JsonLdValue[]
  | { [key: string]: JsonLdValue }

export function JsonLd({ data }: { data: JsonLdValue }) {
  const nonce = getCspNonce()

  return (
    <script
      nonce={nonce}
      type="application/ld+json"
      suppressHydrationWarning
      dangerouslySetInnerHTML={{
        __html: JSON.stringify(data).replaceAll('<', '\\u003c'),
      }}
    />
  )
}
```

Implementation rules:
- `src/lib/csp.ts` is the only nonce accessor used by app code.
- In staging and production, Nginx must generate and forward `X-CSP-Nonce`; the app must not generate an independent fallback nonce because it would not match the CSP header.
- Local development may run without a nonce only when no nonce-based CSP header is enforced.
- Only render the `csp-nonce` meta tag when a nonce exists; do not render an empty `content` attribute.
- Every inline `<script>` must receive `nonce={nonce}`.
- The pre-hydration theme bootstrap script is the only approved executable inline-script `dangerouslySetInnerHTML` exception in the stack baseline. It must be a fixed static string, receive `nonce={nonce}`, and must not interpolate user data or request data.
- JSON-LD is the only approved non-executable data-script `dangerouslySetInnerHTML` exception. JSON-LD scripts must receive `nonce={nonce}` and escape `<` as `\\u003c`.
- The client helper must return `undefined`, not `""`, when the meta tag is missing.
- Do not generate a separate browser nonce.
- Do not call `crypto.randomUUID()` in client code for CSP nonce.

### 2.2 TanStack Ecosystem

The following TanStack libraries are all first-class members of the stack:

| Library | Purpose | Priority |
|---|---|---|
| **TanStack Query** | Server state, data fetching, caching, background sync | Primary — exhaust this before reaching for Zustand |
| **TanStack Router** | Type-safe file-based routing | Required (bundled with Start) |
| **TanStack Form** | Submit-style form state management, paired with Zod | Required for submit-style forms |
| **TanStack Table** | Headless table / datagrid | Required when building interactive or data tables |
| **TanStack Virtual** | List/grid virtualization | Required for long scrolling lists that render more than 100 items at once |

**TanStack Query is the default for all server state.** Before reaching for Zustand, ask: "Is this state derived from the server?" If yes, it belongs in a Query, not a store.

### 2.3 Table standards

Interactive data tables built with TanStack Table should implement the following by default. Simple display tables, key-value summaries, static comparison tables, and compact action/detail tables may omit features that do not fit the content, but the omission must be obvious from the table's purpose or noted in the component review.

**Data table features (default for interactive data tables):**
- Column filtering. Client-side tables filter in memory; server-side tables send filter parameters to the server.
- Global search. Client-side tables may search across visible columns; server-side tables must search the authoritative dataset on the server rather than only the current page.
- Column sorting. Client-side tables sort in memory; server-side tables send sort parameters to the server.
- Show/hide columns through an accessible column visibility menu when the table has enough columns for this to matter.
- Accessible empty, loading, error, and no-results states.

**Pagination strategy** is determined by the nature of the data:

| Data type | Pagination strategy | Rationale |
|---|---|---|
| **Master data** — slow-growing reference records (products, categories, users, settings) | **Client-side pagination** | Full dataset fits in memory; no round-trips per page change; instant UX |
| **Transactional data** — fast-growing records (orders, payments, events, logs, audit trails) | **Server-side pagination** | Dataset grows unboundedly; loading all rows is a performance and memory risk |

When in doubt: if the table will contain more than ~5,000 rows within 12 months at normal growth, use server-side pagination.

Client-side pagination uses TanStack Table's built-in `getPaginationRowModel`. Server-side pagination uses `manualPagination: true` and passes pagination state into the TanStack Query key. Inside TanStack Table, `pageIndex` is zero-based. In URLs, use a human-readable one-based `page` parameter and convert at the route/table boundary (`pageIndex = page - 1`, `page = pageIndex + 1`). Virtualization is for rows actually rendered simultaneously in a scrolling viewport; server-paginated tables with small visible page sizes do not need virtualization just because the total dataset is large.

### 2.4 URL state management: nuqs

Filter, search, and sort state for list/detail pages, data tables, and other shareable views must be **persisted in the URL as query parameters**. This makes the state survive hard refreshes, enables deep-linking, and allows users to share filtered views via URL copy-paste. Local-only controls such as command palettes, combobox suggestions, popover searches, and temporary in-component filters may stay in component state when the state is not useful after refresh or URL sharing.

**`nuqs`** is the required solution for shareable URL search param state management.

- `nuqs` provides React hooks (`useQueryState`, `useQueryStates`) that treat URL search params as reactive state — reading from and writing to the URL with the same ergonomics as `useState`.
- It integrates with TanStack Router through `NuqsAdapter` from `nuqs/adapters/tanstack-router`, mounted once in the root route around `<Outlet />`, after verifying the adapter import path against the pinned `nuqs` version.
- For route-level search validation, use nuqs parser maps with `createStandardSchemaV1` in TanStack Router's `validateSearch`, after verifying that helper against the pinned `nuqs` version.
- State survives hard refresh, back/forward navigation, and is shareable via URL — all without any extra persistence logic.

TanStack Router support in `nuqs` is an accepted organization-standard bet. Pin `nuqs` versions in applications and cover filter/search/pagination URL behavior with tests so adapter regressions are caught early.

Route file:

```typescript
// File: src/routes/products/index.tsx
import { createFileRoute } from '@tanstack/react-router'
import { createStandardSchemaV1 } from 'nuqs'
import { tableSearchParams } from '../../features/products/searchParams'
import { ProductsPage } from '../../pages/products/ProductsPage'

export const validateSearch = createStandardSchemaV1(tableSearchParams, {
  partialOutput: true,
})

export const Route = createFileRoute('/products')({
  validateSearch,
  component: ProductsPage,
})
```

Shared search parser map:

```typescript
// File: src/features/products/searchParams.ts
```

Rules:
- Every filterable or searchable list page with shareable state must use `nuqs` for its filter/search/pagination state.
- Do **not** use `useState` or Zustand for filter/search state that belongs in the URL.
- Use `parseAs*` parsers (typed coercion) — never read raw strings from `searchParams` and cast manually.
- For server-side paginated tables, pass normalized search/filter/sort/page values into the TanStack Query key so refetching is automatic when URL state changes. Keep URL `page` one-based and table `pageIndex` zero-based.
- For high-frequency inputs such as search boxes, debounce URL writes. If a page uses route loaders or server functions that re-run from search-param changes, separate immediate input state from committed URL state so every keystroke does not trigger unnecessary server work.

## 3. State Management

### 3.1 Layered state model

| Layer | Tool | What belongs here |
|---|---|---|
| Server state | TanStack Query | Anything fetched from or synchronized with the server |
| Form state | TanStack Form | Submit-style form inputs, field errors, submission state |
| Global client state | Zustand | UI-only state that must persist across routes (e.g., sidebar open/closed, multi-step flow progress, or a hydrated mirror of theme preference) |
| Local component state | `useState` / `useReducer` | Ephemeral UI state scoped to one component |

### 3.2 Zustand rules

- One store per domain slice. Do not create a single global mega-store.
- Persisted store data must be serializable. Actions may be functions, but persisted state must not contain functions, class instances, DOM nodes, or non-serializable objects.
- Prefer derived values (computed inside selectors) over redundant stored state.
- Persist to `localStorage` only when explicitly required (e.g., theme, onboarding step).

### 3.3 Restricted `useEffect` policy

`useEffect` is **banned** for:
- Data fetching (use TanStack Query)
- Derived or computed state (compute during render, use selectors, or memoize only when the computation is demonstrably expensive)
- Cross-component communication (use Zustand or Query invalidation)
- Reacting to prop or state changes only to mirror, copy, or derive another React state value

`useEffect` is **allowed** for imperative synchronization with systems outside React, including:
- Direct DOM API access (e.g., focus management, `ResizeObserver`, canvas drawing)
- Third-party SDK initialization that has no React abstraction (e.g., Sentry bootstrap on mount, analytics init)
- Cleanup of browser subscriptions (e.g., `addEventListener` / `removeEventListener`)
- Reporting page/view analytics or telemetry after navigation
- Synchronizing React state into imperative widgets that do not expose React-friendly bindings

When in doubt: if a `useEffect` is fetching app data, deriving state from other state, or modifying state only because another React value changed, it is wrong. Refactor to a Query, a route loader, an event handler, or a derived value.

Effects that bridge React to external systems must name the external system in code review. If no external system exists, the effect is probably derived state and should be removed.

## 4. Async-First UI Patterns

The product must feel lightweight and seamless. These patterns are part of the baseline:

### 4.1 Optimistic updates

Mutations that change user-visible data should implement **optimistic updates** via TanStack Query's `onMutate` / `onError` / `onSettled` lifecycle when rollback is safe and the expected outcome is predictable. The user should see routine successful actions immediately, with silent background confirmation. Use explicit confirmation UI for destructive, payment, irreversible, inventory-finalization, compliance-sensitive, external-provider-authoritative, or otherwise unsafe-to-rollback actions.

### 4.2 No blocking spinners

- Full-page loading spinners are banned as the default loading pattern. A minimal blocking initialization state is allowed only for documented app bootstrap boundaries such as auth handoff, required environment initialization, or unrecoverable startup checks.
- Use **Suspense boundaries** with skeleton placeholders for initial data loads.
- Use **background refetch indicators** (e.g., a subtle border or icon pulse) for stale-while-revalidate patterns.
- Route transitions use TanStack Router's `pendingComponent` for deferred navigation feedback.

### 4.3 Server-to-client streaming: SSE first

For server-pushed data (notifications, live order status, background job progress):
- Default to **Server-Sent Events (SSE)** — lighter and HTTP/1.1 / HTTP/2 compatible. SSE events should update TanStack Query caches or invalidate queries from application code.
- Use **WebSocket** only when the use case is genuinely bidirectional and low-latency (e.g., live chat, collaborative editing). If you are not sure, use SSE.

### 4.4 HTTP/2

All production deployments must serve browser traffic over **HTTP/2** at the outside-facing gateway. Multiplexed requests reduce latency for parallel asset and API fetches. This is an Nginx deployment requirement for this stack; the internal Bun/TanStack Start server remains reachable only on the Docker network.

## 5. Styling & UI

### 5.1 Tailwind CSS v4+

**Tailwind CSS v4** is the required styling system. No CSS Modules, styled-components, Emotion, or other CSS-in-JS.

- Configuration is CSS-first (in `app.css` via `@theme`), not `tailwind.config.js`.
- Configure class-based dark mode in CSS with Tailwind v4's custom variant syntax, for example `@custom-variant dark (&:where(.dark, .dark *));`.
- Design tokens (colors, typography, spacing) are defined once in the shared CSS theme file and referenced everywhere via `var(--token-name)`.
- Utility classes only. No custom component CSS files unless wrapping a third-party library with no Tailwind support.

### 5.2 Shadcn UI + Sonner

**Shadcn UI** is the primary component library for all products adopting this standard.

**React Sonner (`sonner` package / `shadcn-sonner` component)** is the required toast/notification library for all frontend-owned and fullstack apps. Transient toast-style feedback — mutation errors, important mutation success, form submission results, and background job completion — must use Sonner toasts. No custom toast components, no third-party alternatives.

Install via shadcn:

```bash
bunx shadcn@latest add sonner
```

Place the `<Toaster />` component in the root layout (e.g., `src/routes/__root.tsx`) — rendered once, globally available. Use `toast()` from `sonner` in client-side code to trigger toasts.

```tsx
import { toast } from 'sonner'

toast.success('Saved')
toast.error('Failed to save')
toast('Background job completed')
```

Sonner rules:
- Use success toasts for important completed actions, background jobs, and non-obvious confirmations. Do not toast every routine optimistic mutation if the UI state already confirms success.
- Error toasts on mutation failure with the error message — never silently swallow errors.
- Prefer inline validation or field-level errors for form problems the user can fix in place; use toasts for transient, global, or cross-page feedback.
- Never build a custom toast or snackbar for transient user feedback. Sonner only.
- Style toasts via Tailwind theme tokens (no hardcoded colors).
- Toasts must be dismissible and announced accessibly. Verify Sonner defaults remain enabled when customizing toast rendering.

Rules:
- **Prioritize Shadcn components over custom builds or third-party alternatives.** Before building a custom component, check if Shadcn has one.
- Each product maintains committed Shadcn project configuration (`components.json`) that encodes the project's theme, style, and import aliases. If the organization provides a reusable preset or registry, `components.json` records how the product consumes it.
- Shadcn components are copied into `src/components/ui/` (standard Shadcn convention). Customize them in-place — do not wrap them in an extra abstraction layer.
- Third-party component libraries (e.g., MUI, Ant Design) are **banned** unless a required feature is absent from Shadcn/Radix.
- **The base Shadcn preset or registry (design tokens, project configuration, and base `ui/` components) is maintained in a shared internal repository owned by the adopting organization.** For this organization, the current internal repository is `minia/ui`; replace this name before publishing the standard outside the organization. Full merge rights are held exclusively by the designated architecture owner. Engineers may open PRs to propose token or component changes, but no change is merged without designated architecture owner approval. Every product pulls from this shared repo as the starting point. Products may extend or override tokens locally but must not diverge from the base without an ADR.
- **Configure Shadcn for TanStack Start / non-RSC output and audit generated files for `"use client"` directives.** TanStack Start does not use the Next.js `"use client"` directive model. The preferred fix is project configuration that prevents the directive from being generated (for example non-RSC Shadcn config); if a generated component still includes it, remove it after verifying SSR safety. Browser-only components must be guarded, deferred, or isolated rather than blindly SSR-rendered.
- Use `bunx shadcn@latest ...` only as a generation command. Review generated component diffs and lockfile changes before merge, and pin installed runtime dependencies in `package.json`.

### 5.3 Dark / Light mode

**Dark and Light mode support is required in every product.** No exceptions.

- Implement via Tailwind's `dark:` variant and a `class="dark"` toggle on `<html>`.
- Store the user's preference in `localStorage` under the `theme` key as one of three raw string values: `light`, `dark`, or `system`. This raw browser value is canonical for pre-hydration behavior. Zustand may mirror it after hydration, but the persisted browser value must stay as this raw string so the pre-hydration bootstrap script can read it before React starts.
- Do not use Zustand's default JSON persist format for the `theme` key unless a custom storage adapter preserves the raw string contract required by the bootstrap script.
- Respect `prefers-color-scheme` as the default on first visit.
- Use the CSP-safe pre-hydration theme bootstrap script from the internal CSP reference implementation so dark/light mode does not flicker before React hydrates.
- Design and test both modes before a feature is considered complete.

### 5.4 Charts: Recharts

**Recharts** is the required charting library for standard product charts.

- Do not use Chart.js, Victory, Nivo, or D3 directly for standard chart types.
- All charts must support dark and light mode (pass colors via CSS variables from the Tailwind theme, not hardcoded hex values).
- Charts must be responsive — wrap in a `<ResponsiveContainer>` with `width="100%"`.
- Recharts is composable; build charts from primitives (`<LineChart>`, `<BarChart>`, `<CartesianGrid>`, `<Tooltip>`, etc.) rather than using higher-level wrappers.
- Shadcn chart wrappers are approved when they wrap Recharts and preserve the same theme-token and responsiveness requirements.
- For complex custom visualizations that Recharts cannot express cleanly, D3 is the approved fallback. Document the reason inline.
- Charts that depend on browser layout measurement, container size, or heavy client-side rendering should be considered deferred hydration candidates. Do not force chart code into the startup bundle unless the chart is above the fold and needed for the primary task.

### 5.5 Animations

Simple, purposeful motion is part of the standard product feel. Use it where it clarifies state, hierarchy, or continuity. Heavy, gratuitous, inaccessible, or purely decorative animations are banned.

**Two-tier approach:**

**Tier 1 — Tailwind CSS transitions (default):** Use Tailwind's `transition-*`, `duration-*`, `ease-*`, and `animate-*` utilities for simple state-driven transitions. This is zero-dependency and should cover the majority of cases.

The `animate-in`, `fade-in`, and `slide-in-*` utilities shown below require the organization Shadcn/Tailwind preset or another approved animation utility. If that preset is absent, use core Tailwind transition utilities only.

```html
<!-- fade-in on mount via opacity transition -->
<div class="opacity-0 animate-in fade-in duration-200">...</div>

<!-- slide-up with fade -->
<div class="animate-in slide-in-from-bottom-4 fade-in duration-300">...</div>
```

**Tier 2 — Motion for React (`motion` package, `motion/react` import):** Use for route-level page transitions, gesture-driven interactions, and animations that require choreography or exit transitions. Keep usage minimal — if Tailwind can do it, use Tailwind.

Approved animation types:
- **Fade in / fade out** — for modals, tooltips, popovers, toasts appearing and disappearing
- **Slide up / slide down** — for sheets, drawers, dropdown panels entering from an edge
- **Slide in from side** — for route/page transitions
- **Scale** — for context menus, popover reveal (subtle, 0.95 → 1.0 scale)

Banned animation types:
- Bouncing or spring physics on data tables, lists, or navigation
- Full-screen transition overlays that block content
- Animations longer than 400ms (use 150–300ms as the target range)
- Animations that play on every render (only play on state change or mount)

Accessibility rules:
- Respect `prefers-reduced-motion`; disable nonessential motion and replace necessary transitions with near-instant state changes.
- Do not use animation as the only cue for state change, validation, success, failure, or progress.
- Verify animated components remain keyboard-usable and screen-reader understandable while entering, exiting, and loading.

## 6. Authentication

**Better Auth** is the required authentication library for all fullstack products adopting this standard. Frontend-owned products that delegate authentication entirely to an external backend must document that boundary and must not implement ad hoc client-only session logic.

Rules for fullstack products:
- Configure the Better Auth server in `src/lib/auth.ts` (server-side).
- Configure the Better Auth client in `src/lib/auth-client.ts` (client-side).
- Use Drizzle as the Better Auth database adapter (shared with the app's ORM setup).
- Session management is handled entirely by Better Auth. Do not implement custom session logic.
- Supported providers per product are configured in `auth.ts`. OAuth providers (Google, etc.) are preferred over email/password where the product UX allows it.
- Protected routes are enforced with TanStack Router route-level `beforeLoad` guards backed by server-side session checks, not component-level checks.

## 7. Database & ORM

### 7.1 Database: PostgreSQL

PostgreSQL is the only supported database for fullstack products adopting this standard. Frontend-owned products with no owned server-side persistence do not need a database service.

- Do not use MySQL, SQLite (in production), or MongoDB.
- For local development, PostgreSQL runs in Docker Compose when the product owns PostgreSQL-backed persistence.

### 7.2 ORM: Drizzle

**Drizzle ORM** is the required ORM for products that access PostgreSQL from application code.

**Driver selection:** Drizzle supports multiple PostgreSQL drivers. Priority order:
1. **`bun:sql` (Bun's native PostgreSQL driver)** — use this by default after verifying required production capabilities for the product, including pooling, TLS, PgBouncer behavior, prepared statements, migrations, and observability. Available in Bun ≥ 1.2 via `import { SQL } from "bun"`. Drizzle integrates via `drizzle-orm/bun-sql`. Fastest option; no additional dependency.
2. **`postgres` (the `postgres.js` driver)** — use when pooling, TLS, PgBouncer, prepared statements, migration behavior, observability, a specific query, or another production requirement is unsupported or insufficiently proven with the Bun native driver. Document the reason inline.
3. Other drivers (`pg`, `neon`, etc.) — banned unless there is an explicit infrastructure reason (e.g., serverless edge deployment).

Other Drizzle rules:
- Schema is defined in `src/db/schema.ts` (or split by domain under `src/db/schema/`).
- Migrations are managed with `drizzle-kit`. Migration files are committed to the repo.
- Do not use raw SQL strings in application code unless Drizzle's query builder genuinely cannot express the query. Document the exception inline.
- Do not use Prisma, TypeORM, Sequelize, or any other ORM.

### 7.3 Row-Level Security (multi-tenancy)

**Row-Level Security (RLS) is the preferred end-state for multi-tenant products, but it is not mandatory in Phase 1 by default.**

RLS remains the strongest PostgreSQL-level isolation model and should be adopted once the product's request lifecycle, transaction boundaries, and PgBouncer behavior are stable enough to support it safely.

Rules:
- Every tenant-scoped table must have a `tenant_id` (or equivalent) column with a `NOT NULL` constraint.
- Every multi-tenant product must implement one of two explicit modes:
  1. **Phase 1 application-level isolation mode** — tenant scoping enforced in application code and repository boundaries, with automated leakage tests
  2. **RLS mode** — PostgreSQL RLS enforced via migration-defined policies
- In Phase 1 application-level isolation mode:
  - all seller/customer-facing queries must derive tenant context from the authenticated session, never from client-provided identifiers alone
  - repository/service methods must require tenant identifiers explicitly
  - integration tests must assert that a tenant cannot read or modify another tenant's rows even if application-level route guards are bypassed
  - tenant leakage integration tests are required for every tenant-scoped repository or server function path
- In RLS mode:
  - RLS policies are defined in `drizzle-kit` migration files and applied as part of the standard migration workflow
  - the application sets the current tenant context with transaction-local PostgreSQL state, for example `SET LOCAL app.current_tenant_id = '...'`, inside the active transaction that performs tenant-scoped queries
  - plain session-level `SET` is banned for request tenant context unless the connection is dedicated to that request and reset before reuse; pooled connections must not retain tenant context after a request completes
  - policies must cover `SELECT`, `INSERT`, `UPDATE`, and `DELETE`
  - policy enforcement tests must verify cross-tenant denial for `SELECT`, `INSERT`, `UPDATE`, and `DELETE`
  - bypass queries (for example migrations or privileged admin paths) must use a dedicated database role or separate privileged connection path

**When to defer RLS:**
- transaction-pooled PgBouncer or unclear connection ownership makes tenant-context handling fragile in an early-stage codebase
- request/transaction boundaries are still changing rapidly
- the team can enforce strict repository boundaries and leakage tests faster than it can safely enforce session-variable-based RLS

If RLS is deferred, document it as an explicit product-level decision and define the trigger for revisiting it (for example Phase 2 scale-up or multi-instance production maturity).

## 8. Forms & Validation

### 8.1 TanStack Form + Zod

All submit-style forms use **TanStack Form** for state management. Filter/search controls that only update URL state may use `nuqs` directly and do not need TanStack Form. All validation schemas use **Zod** when the input is submitted to a server function or persisted.

- Define a Zod schema for every submit-style form. This schema is the source of truth for field shapes and validation rules.
- Pass the Zod schema to TanStack Form validators through the Standard Schema-compatible `validators` API, such as `validators: { onChange: schema }` or the product's chosen validation timing, after verifying the validator shape against the pinned TanStack Form version.
- The same Zod schema is reused on the server function for server-side validation. Never trust client-side validation alone.
- Do not use React Hook Form, Formik, or any other form library.

### 8.2 Server-side validation

Every server function that accepts user input must:
1. Validate input with a Zod schema before any database or business logic.
2. Return typed errors. Submit-style form handlers must return errors that TanStack Form can map back to field-level messages; non-form server functions should return typed domain errors that callers can handle explicitly.

## 9. Progressive Web App (PWA)

PWA support is **optional by default**. A web product should add PWA capabilities only when the product explicitly benefits from installability, offline behavior, background sync, push notifications, or mobile-app-like distribution.

Baseline requirements for every web product:
- Mobile-responsive, mobile-first layout. Design from the smallest breakpoint first, then expand to tablet and desktop. Test on 375px width as the minimum target.
- Mobile viewport meta tag (`width=device-width, initial-scale=1`).
- Touch-friendly interaction targets for primary actions.
- Safe behavior on poor or intermittent network conditions.

Recommended when the product is used heavily on mobile:
- `manifest.json` with app name, icons, theme color, and `display: standalone`.
- App icons sized for common install surfaces.
- Basic installability QA on Android Chrome and iOS Safari.

Required only when offline/PWA mode is explicitly adopted:
- Service worker with a documented caching strategy.
- Network-first caching for API/data requests that can tolerate retries.
- Cache-first strategy for static versioned assets.
- Offline fallback page for unavailable navigation requests.
- Clear invalidation rules so stale app shells or stale API responses do not break critical flows.

Do not add a service worker by default. A poorly designed service worker creates stale-cache bugs, broken deploys, and confusing support issues. Treat PWA mode as a product-level decision, not a universal frontend default.

## 10. Monitoring & Observability

### 10.1 Sentry (optional, runtime-toggled)

Sentry is the **standard** error and performance monitoring tool, but it is **optional** — it must be possible to run the product without Sentry configured (local development, environments where Sentry is not yet set up).

**Enable/disable via environment variable:**

```env
# .env
SENTRY_ENABLED=true        # set to false or omit to disable
SENTRY_DSN=https://...     # required only when SENTRY_ENABLED=true
```

At application startup, check `process.env.SENTRY_ENABLED === "true"` before initializing Sentry. If the flag is false or absent, skip initialization entirely. If `SENTRY_ENABLED=true` but `SENTRY_DSN` is absent, fail fast in production and warn in local development. TanStack Start has server and browser execution paths; products that enable Sentry must document where server-side and client-side initialization happen and must verify the compatible SDK entry points for the pinned runtime and framework versions.

Rules when Sentry is enabled:
- Verify Bun/runtime SDK compatibility for the specific product before enabling Sentry, then initialize the compatible Sentry SDK at the app entry point.
- Initialize server-side and browser-side Sentry separately when the SDK requires separate entry points; do not assume one client entry captures SSR/server-function failures.
- Capture unhandled exceptions and unhandled promise rejections.
- Use Sentry's performance tracing for server functions and critical user flows.
- Do not log sensitive user data (PII, tokens, passwords) to Sentry. Scrub before capture.
- Each product has its own Sentry project (DSN in `.env`, never hardcoded).

Baseline observability rules for every production deployment:
- Emit structured application logs to stdout/stderr so the container platform can collect them.
- Include a request ID or trace ID in server logs for request-handling paths.
- Keep `GET /ready` minimal and unauthenticated for internal health checks; expose detailed diagnostics only through authenticated operational tooling.
- Record security-sensitive events such as login failures, permission denials, and tenant access denials without logging secrets or full payloads.
